| 1 | MC-1 | REPRODUCED | Critical | With `fixedTimeLimit` and a callable that ignores interrupts (e.g. a blocking socket read), a timed-out attempt keeps running beside later attempts and after `call()` returns or throws; in the reproduction its late side effect overwrote the value `call()` had returned and the service saw two concurrent requests from one call, with nothing to correct it. Reached through `fixedTimeLimit(d, unit)` + `Retryer.call`; the pool cannot be shut down, so there is no recovery. |
| 3 | MC-3 | FALSE POSITIVE | — | Phase 4 found the reached state is the documented timeout outcome (callers see exactly an ordinary timeout) and repaired the over-strict invariant; this disposition carries no severity. |
| 4 | MC-4 | REPRODUCED | Critical | With `fixedTimeLimit`, an interrupt of the thread in `call()` (`Thread.interrupt`, `Future.cancel(true)`, `shutdownNow()`) is swallowed: retrying continues with the interrupt status cleared, a completed attempt can be discarded and run again, and `cancel(true)`/`shutdownNow()` did not stop a `wrap()` task (18 more service calls in 2 s).
