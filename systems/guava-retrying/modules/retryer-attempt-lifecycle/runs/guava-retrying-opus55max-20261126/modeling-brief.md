# Modeling Brief: guava-retrying 2.0.0

## 1. System Overview

- **System**: rholder/guava-retrying 2.0.0, a Java library that retries a `Callable` until it succeeds or a stop strategy stops it. Analyzed checkout `177b6c9` (src/main is byte-identical to tag `v2.0.0` = `c3e1c37`; upstream inactive since 2016). Built against Guava 22.0 with an out-of-tree Maven build (`analysis-evidence/build/pom.xml`, JDK 21 `--release 8`); the 36 existing tests pass.
- **Language / scale**: Java, 13 files, 1,457 lines, **701 non-comment code lines** (WaitStrategies 220, Retryer 180, RetryerBuilder 118, StopStrategies 55, AttemptTimeLimiters 54, RetryException 23, BlockStrategies 17, interfaces ≤ 11 each). Guava 22.0 `SimpleTimeLimiter` (320 lines) is environment that `AttemptTimeLimiters` depends on; its behavior is described here and must be modeled, but it is not a target.
- **Category**: **Category B (Concurrent / Runtime)**. There is no network, disk or message passing. The concurrency is a thread handoff from the caller to executor workers (`SimpleTimeLimiter` + `FutureTask`), cancellation by interrupt, the caller's and workers' interrupt flags, and a mutable listener list shared between the builder's thread and threads running `Retryer.call`. Later phases should use concurrent-style modeling (per-thread program counters, FutureTask state, split actions at CAS / park / interrupt boundaries) and concurrent-style trace validation (per-thread JVM-level events).
- **Reference algorithm**: none formal ("Retry library for Callables"). The contract is the Javadoc (§ 1.6).
- **Key architectural choices** (each one is the root of a Scenario):
  1. The per-attempt time limit delegates to Guava's deprecated `SimpleTimeLimiter.callWithTimeout(callable, d, unit, amInterruptible=true)` (`AttemptTimeLimiters.java:105-108`). The attempt runs on an executor worker while the caller blocks in `Future.get(timeout)`. On a timeout or a caller interrupt, Guava calls `future.cancel(true)` and returns at once; it never waits for, joins or tracks the worker (`SimpleTimeLimiter.java:152-158,164-166`). → Scenario 1.
  2. The two-argument `fixedTimeLimit(d, unit)` creates a private `Executors.newCachedThreadPool()` per limiter instance (`AttemptTimeLimiters.java:89-91` → `SimpleTimeLimiter.java:81-84`): non-daemon threads, 60 s keep-alive, never shut down, no API to reach it. → Scenario 1.
  3. `Retryer.call` turns **every** `Throwable` out of the attempt into an `ExceptionAttempt` (`catch (Throwable t)`, `Retryer.java:159-164`): callable exceptions, `Error`s, timeouts, caller interrupts, executor rejection and limiter misconfiguration all look alike. → Scenarios 2 and 4.
  4. Interrupts are handled at exactly one place, the catch around `blockStrategy.block` (`Retryer.java:177-182`); `Thread.sleep(0)` under `noWait` is the de facto interrupt checkpoint. → Scenario 2.
  5. `RetryerBuilder.build()` passes the builder's own `ArrayList` of listeners to each Retryer, which stores it without copying (`RetryerBuilder.java:40,196`; `Retryer.java:137`). Every other builder field is captured by value. → Scenario 3.
  6. Listener notification, rejection predicate, stop check, wait computation and block run **outside** the attempt try/catch, and the computed sleep is never validated (`Retryer.java:166-182`). → Scenario 5.
  7. The loop counter is an `int` (`Retryer.java:157`) although `Attempt.getAttemptNumber()` is `long`. → Scenario 5.
- **Concurrency model**: `Retryer.call` runs on the calling thread. With `noTimeLimit`, the callable, listeners and strategies all run on that thread, in order. With `fixedTimeLimit`, only the callable moves to a worker of the limiter's executor (default cached pool, or a user `ExecutorService`); listeners and strategies stay on the caller. A Retryer has only final fields (`Retryer.java:47-52`) and may be shared by any number of callers, directly or through `wrap()` tasks on an executor (class Javadoc `Retryer.java:39-40`; maintainer in #35: "Yes, they should all be thread-safe."). Built-in strategies are stateless; `RandomWaitStrategy` shares one thread-safe `java.util.Random` (`WaitStrategies.java:249`). A `FixedAttemptTimeLimit` shares one executor among all Retryers and callers that use it.

### 1.2 Baseline: a time-limited attempt (`AttemptTimeLimiters.java:105-108` → Guava 22.0 `SimpleTimeLimiter.java:142-168` → JDK `FutureTask`)

Caller side (JDK line numbers are JDK 21 unless noted):

- **a.** `checkNotNull(callable)`, `checkPositiveTimeout(d)` (`SimpleTimeLimiter.java:145-147,317-319`) → `IllegalArgumentException` for d ≤ 0, which `fixedTimeLimit` never validated (D-11).
- **b.** `future = executor.submit(callable)` (`:149`) → `RejectedExecutionException` if the executor is shut down or full (D-10). The default cached pool hands the task to an idle thread or creates a new one (SynchronousQueue).
- **c.** `future.get(d, unit)` (`:154`) → `FutureTask.get` (`FutureTask.java:197-206`) → `awaitDone` (`:446-495`). On JDK 9+ completion is checked before `Thread.interrupted()` (`:460` then `:469`); **JDK 8 checks the interrupt first** (JDK 8 `FutureTask.java:402`). Four endings: value; `ExecutionException`; `TimeoutException` when the deadline passes while the state is still NEW or COMPLETING (`:474`, `:490`); `InterruptedException` with the caller's flag cleared.
- **d.** `InterruptedException` → `future.cancel(true)`, rethrow (`SimpleTimeLimiter.java:155-157`).
- **e.** `ExecutionException` → `throwCause(e, true)` (`:162-163,251-269`): rethrows the cause if it is an `Exception` or `Error`, after concatenating the caller's stack onto it (D-12); any other `Throwable` is rethrown still wrapped (D-13).
- **f.** `TimeoutException` → `future.cancel(true)`, throw `UncheckedTimeoutException(e)` (`:164-166`). The boolean result of `cancel` is ignored (D-2).

Worker side: `FutureTask.run` (`FutureTask.java:307-337`) returns immediately if the state is no longer NEW (a task cancelled while queued never runs its body); otherwise it runs the body, then `set` / `setException` CAS NEW→COMPLETING (`:281-305`), which **fails silently if `cancel` won**, dropping the result. `finally` waits out INTERRUPTING (`handlePossibleCancellationInterrupt`, `:381-397`) but does not clear the interrupt; `ThreadPoolExecutor.runWorker` clears a stale interrupt before the next task (`ThreadPoolExecutor.java:1136-1140`).

`cancel(true)` (`FutureTask.java:164-182`) = CAS NEW→INTERRUPTING, `runner.interrupt()`, set INTERRUPTED. It neither waits for the body nor removes a queued task from a `ThreadPoolExecutor` queue.

**Atomicity boundaries that matter**: (i) between `awaitDone` deciding "timed out" and the `cancel` CAS (D-2 window, ~2–3 µs); (ii) between the body's return and the worker's `set` CAS (a cancel in between drops a finished result); (iii) `cancel` CAS vs. the worker's start (a task cancelled before start never runs: D-4, D-5 with 0 invocations); (iv) `submit` vs. `get` (a pending caller interrupt is consumed by the first `get`, D-5).

### 1.5 Baseline: sharing a Retryer

`call()` keeps all per-call state in locals (`Retryer.java:156-158`), so concurrent calls do not interfere through the Retryer itself. What they do share: the listener list (Scenario 3), the time limiter's executor (Scenario 1: a bounded pool lets one caller's stuck attempts make another caller's attempts time out before they start, D-4), and the static `Random`. `wrap()` (`Retryer.java:195-197,301-320`) just calls `retryer.call(callable)` on the executor thread, so executor cancellation reaches `call()` only as an interrupt (Scenario 2, D-7). `RetryerCallable`'s fields are non-final, but submission to an executor publishes them safely (refuted as a defect).

### 1.6 Documented contracts used for invariants

- **C1** sequence: "A retryer, which executes a call, and retries it until it succeeds, or a stop strategy decides to stop retrying" (`Retryer.java:31-35`).
- **C2** thread safety: "A retryer is thread-safe, provided the arguments passed to its constructor are thread-safe" (`Retryer.java:39-40`); #35: "Yes, they should all be thread-safe."
- **C3** outcomes of `call()` (`Retryer.java:146-153`): returns the result; "@throws ExecutionException if the given callable throws an exception, and the rejection predicate considers the attempt as successful"; "@throws RetryException if all the attempts failed before the stop strategy decided to abort, or the thread was interrupted. Note that if the thread is interrupted, this exception is thrown and the thread's interrupt status is set."
- **C4** "If an attempt is rejected, the retryer will retry the call, unless the stop strategy indicates otherwise or the thread is interrupted" (`Retryer.java:59-61`).
- **C5** time limit: "A rule to wrap any single attempt in a time limit, where it will possibly be interrupted if the limit is exceeded" (`AttemptTimeLimiter.java:22`); "limit the duration of any particular attempt" (`RetryerBuilder.java:113`); "to prevent from any single attempt from spinning infinitely" (`Retryer.java:73`).
- **C6** Guava `TimeLimiter.callWithTimeout` (`TimeLimiter.java:80-93`): a call that "finished before the limit is reached" is propagated "exactly as-is"; at the limit "we attempt to abort the call"; with `interruptible` true it responds "to thread interruption by aborting the operation and throwing InterruptedException". (For proxies: "aborting the target method call is of secondary concern", `:47-48`.)
- **C7** listeners: fire for every attempt "before the rejection predicate and stop strategies are applied" (`RetryListener.java:29-30`); "Adds a listener that will be notified of each attempt that is made" (`RetryerBuilder.java:56`).
- **C8** "The number, starting from 1, of this attempt" (`Attempt.java:74`); waits and delays are in milliseconds (`WaitStrategy.java:27`, `Attempt.java:81-83`).
- **C9** strategies: `join` "wait time which is total of all wait times" (`WaitStrategies.java:220`); exponential and Fibonacci grow "up to the maximumTime" (`:130`, `:172`); `stopAfterAttempt` "stops after N failed attempts" (`StopStrategies.java:49-52`); `stopAfterDelay` stops when the time since the first attempt "has exceeded the given delay" (`:75-79`).

**Q1 documentation assessment**: C5 ("possibly interrupted") and Guava's proxy note admit that a timed-out attempt may not be stopped. Nothing in guava-retrying admits that the timed-out attempt keeps running **alongside later attempts** or **after `call()` returns**, that a **finished result can be discarded and the work repeated**, or that **worker threads accumulate and outlive the retryer**; C1 describes a sequence, and the `fixedTimeLimit` factories carry no warning. These outcomes are all reachable (D-1, D-2, D-3, D-4) and are treated as defects pending confirmation.

## 2. Scenarios

### Scenario 1: Time-limited attempts escape the attempt sequence

**Mechanism**: Guava's `SimpleTimeLimiter` returns control to the caller as soon as the deadline passes (or the caller is interrupted), cancels the `FutureTask` with an advisory interrupt and never waits for or tracks the worker, while `Retryer.call` immediately starts the next attempt; attempt bodies therefore outlive their `Attempt`, completions racing the deadline are discarded, and the executor fills with zombie attempts.

**Evidence**:
- Historical: PR #1 / `7e474be` introduced the limiter (logic unchanged since 1.0.3); #92 (open) non-daemon pool threads delay JVM exit by ~60 s; #18 (open) maintainer: the `SimpleTimeLimiter` limiter "can be fairly wasteful with respect to resources"; #29 (timeouts are ordinary exceptions). Forks changed only pool lifecycle: rhuffman/re-retrying `5234118` (one static pool, still non-daemon), itning/guava-retrying3 `affae9e` (removed the no-executor factory). No upstream or fork report of overlapping attempts or discarded completions.
- Code analysis: `SimpleTimeLimiter.java:155-157,164-166` (cancel then return, no join; `cancel` result ignored); `AttemptTimeLimiters.java:57-60,85,89-91` (private per-limiter cached pool, no shutdown path; `AttemptTimeLimiter.java:27-34` has only `call`); `Retryer.java:160` (same `Callable` instance for every attempt); JDK `FutureTask.java:164-182` (cancel), `:281-305` (late set loses CAS), `:307-337` (cancelled-while-queued task skips its body), `:446-495` (timeout decision).
- Probes (code-analysis phase, unmodified 2.0.0 + Guava 22.0, JDK 11 and/or 21): `timelimit/P1Overlap` (4 concurrent attempts; 3–4 finished after `call()` ended), `timelimit/P2Race` (83/20,000 and 60/20,000 NORMAL futures reported as timeouts and re-executed), `timelimit/P3ThreadGrowth` (20 attempts → 20 threads stuck forever; JVM never exits), `timelimit/P4Executors` (bounded pools: attempts that never ran counted as failures), `sharing/SharedLimiterStarvation`, `sharing/WrapSameExecutor` (livelock), `interrupt/IntProbe4` (a caller interrupt also leaves the cancelled attempt running).

**Affected code paths**: `FixedAttemptTimeLimit.call` (`AttemptTimeLimiters.java:105-108`); `SimpleTimeLimiter.callWithTimeout` (`:142-168`); `FutureTask.run/set/setException/cancel/get`; `ThreadPoolExecutor` worker loop; `Retryer.call` (`:157-184`).

**Suggested modeling approach**:
- Variables: per caller `pc` (§ 1.1 steps with step 2 expanded to Submit / Wait / TimeoutDecide / Cancel / Classify); per attempt task `state ∈ {NEW, COMPLETING, NORMAL, EXCEPTIONAL, CANCELLED, INTERRUPTING, INTERRUPTED}`, `runner`, `body ∈ {NotStarted, Running, Returned, Threw}`, `owner` call, attempt number; per worker `busy` task and `intr` flag; executor `kind ∈ {Cached, Bounded}`, `queue`, `capacity`, `shutdown`; callable behavior per attempt chosen nondeterministically from {returns, throws, honors-interrupt, ignores-interrupt, blocks-forever}; ghost `callEnded[c]`.
- Actions: `Submit` (or `Reject`), `WorkerStart` (skip tasks that are not NEW), `BodyStep` / `BodyEnd`, `WorkerSetCAS` (fails after cancel), `WorkerFinally` + `ClearInterrupt` (TPE), `WaitDone`, `DeadlineExpire` (nondeterministic while waiting), `TimeoutDecide`, `Cancel`, `Classify`; optionally `IdleExit` for the cached pool's keep-alive.
- Granularity: `TimeoutDecide` and `Cancel` must be separate actions (D-2 lives between them); `BodyEnd` and `WorkerSetCAS` must be separate; `Submit` and `WorkerStart` must be separate (cancelled-before-start). Do not collapse a time-limited attempt into one action.

**Priority**: High
**Rationale**: Priority question Q1; four probe-reproduced defects with no upstream report; the mechanism is pure thread handoff and cancellation, where TLA+ exhaustively explores timeout/complete/cancel interleavings that tests hit only statistically (D-2 at ~0.4 %).

### Scenario 2: Interrupts consumed inside an attempt are never restored

**Mechanism**: `Retryer.call` restores the interrupt status only around the inter-attempt sleep (`Retryer.java:177-182`); an `InterruptedException` raised while the attempt runs — by Guava's interruptible `Future.get` (flag already cleared) or by an interruptible callable on the caller thread — is caught by `catch (Throwable)` and becomes an ordinary failed attempt, after which the rejection predicate, not the interrupt, decides what happens.

**Evidence**:
- Historical: no upstream issue, PR or commit mentions interrupt handling (only #63 quotes the sleep catch); the catch structure dates from the original import `c531b61`. The derivative rhuffman/re-retrying confirms the mechanism independently: its issue #32 ("interrupt during callback does not stop retrying, contrary to the Javadoc") and commits `e2d01c3`, `f1ff0bf` (rethrow `InterruptedException`). Open PR #101 would skip `Thread.sleep(0)`, removing the only interrupt checkpoint under `noWait` (regression risk confirmed by an archaeology probe).
- Code analysis: `Retryer.java:159-164` (catch-all), `:170-174` (predicate / stop decide), `:177-182` (only restore point); `AttemptTimeLimiters.java:107` (`amInterruptible=true`); `SimpleTimeLimiter.java:152-158`; Guava documents the interruptible mode as "aborting the operation and throwing InterruptedException" (`TimeLimiter.java:88-93`), so the obligation sits with `Retryer`. JDK 8 vs 9+ order in `awaitDone` (§ 1.2 c).
- Probes (JDK 11 and 21): `interrupt/IntProbe` (H2.1 a–f, H2.3 a–d), `interrupt/IntProbe2` (H2.2 pre-interrupted: 290/300 returned normally with flag clear; with `retryIfRuntimeException()` 298/300 threw `ExecutionException(InterruptedException)` with 0 invocations), `interrupt/IntProbe3` and `sharing/WrapCancelZombie2` (cancelled / `shutdownNow` `wrap()` tasks keep retrying, executor never terminates).
- Correct paths confirmed: an interrupt that lands during listeners, predicate, stop or wait computation, or during the sleep, yields `RetryException` with the flag set (`sleep(0)` throws when flagged on JDK 8/11/21); a successful attempt returns with the flag still set (acceptable).

**Affected code paths**: `Retryer.call` (`:155-185`); `RetryerCallable.call` (`:317-319`); `SimpleTimeLimiter.callWithTimeout` (`:152-158`); `ThreadSleepStrategy.block` (`BlockStrategies.java:46`).

**Suggested modeling approach**:
- Variables: `intr[t]` for the caller and every worker; ghosts `interruptDelivered[c]`, `ieOnCaller[c]` (an `InterruptedException` was raised on the caller thread), `flagAtExit[c]`, `outerCancelled[c]` for `wrap()`; configuration constants `PredicateMatchesIE`, `StopAfter` (attempt bound or never).
- Actions: environment `Interrupt(caller)` enabled at every caller step (budget 1–2); `CancelOuter(c)` (sets `outerCancelled`, interrupts the thread running `call()`); caller `WaitInterrupted` (JDK 9+ order: completion first; optional constant for JDK 8 order); for noTimeLimit an interruptible callable step on the caller thread; `Block` with JDK semantics (negative → IAE first; flag set → IE, clear, restore, `RetryException`; otherwise sleep, interruptible).
- Granularity: an interrupt must be able to arrive between any two caller steps; keep `Submit` and `Wait` separate (the pending-interrupt path); keep a caller-side `InterruptedException` (caller flag cleared) distinct from a worker-side one that the callable throws while the caller is not interrupted (that one is legitimately a callable failure).

**Priority**: High
**Rationale**: Priority question Q2; an explicit Javadoc promise (C3, C4) is broken in every predicate class, and the `wrap()` consequence (uncancellable tasks, executors that never terminate) is a real lifecycle bug; no upstream report.

### Scenario 3: Listener list aliased between `RetryerBuilder` and running Retryers

**Mechanism**: `build()` hands the builder's own `ArrayList` to every Retryer — the only builder state not captured by value — so a later `withRetryListener` both changes the listener set of already-built Retryers and races with the fail-fast iteration in `Retryer.call`, which runs after the attempt and outside its try/catch.

**Evidence**:
- Historical: #48 (open, no replies) reports the aliasing; #35 (thread-safety claim); #13 and open PR #43 (builder reuse; maintainer: "might have some thread safety implications"). Introduced by `1edb757` (PR #37), kept by `54a2a4d` (List). No fork fixed it (re-retrying later made predicates shared as well).
- Code analysis: `RetryerBuilder.java:40,61-65,196`; `Retryer.java:52,137,166-168`; fail-fast `ArrayList.Itr` (JDK 21 `ArrayList.java:1043,1093`).
- Probes: `sharing/SharedListenerCME` (deterministic latch schedule: CME at `Retryer.java:166`, side effect executed once, predicate and stop never called; JDK 11 and 21), `sharing/RacyListenerStressLogging` (9,369 of 9,406 uncoordinated modifications caused CME), `sharing/ListenerSetDrift` (#48 in flight).

**Affected code paths**: `RetryerBuilder.withRetryListener`, `RetryerBuilder.build`, the `@Beta` six-argument `Retryer` constructor, the listener loop in `Retryer.call`.

**Suggested modeling approach**:
- Variables: `blist` (sequence of listener ids), `bmod` (modification count), `cfgAtBuild[r]` (ghost snapshot), per caller iterator `cursor` and `expMod`, `notified[c]`.
- Actions: builder thread `AddListener(l)` and `Build(r)` (alias + ghost snapshot); caller `IterInit` (`expMod := bmod`), `HasNext` (`cursor # Len(blist)`), `Next` (CME if `bmod # expMod`, else notify and advance). Each notification is its own step (a listener may block).
- Granularity: one atomic `AddListener` suffices under sequential consistency; optionally split it (modCount++ / store / size++) to expose the "no CME, listener silently skipped" branch. Do not model JMM reorderings.

**Priority**: Medium
**Rationale**: Priority question Q3; known root cause (#48) but a new, worse consequence (undocumented exit after the side effect, lost outcome); tiny state that composes with the same caller `pc` as Scenarios 1–2.

### Scenario 4: Attempt-outcome attribution at the time-limiter boundary

**Mechanism**: `Retryer.call` cannot distinguish failures of the callable from failures of the attempt machinery: timeouts, caller interrupts, executor rejection, an invalid limit and Guava's re-wrapping all leave `attemptTimeLimiter.call` as exceptions and become `ExceptionAttempt`s that predicates, the stop budget, listeners and `RetryException` attribute to the callable.

**Evidence**:
- Historical: #29 (open; maintainer: "I agree with your assessment and would also consider it a bug"; timeouts are retried only when a predicate accepts `UncheckedTimeoutException`); #67 (Errors wrapped, open). PR #95, PR #103 and several forks switch to the three-argument `callWithTimeout`, which would change these shapes again (timeouts become checked `TimeoutException`, callable failures get wrapped).
- Code analysis: `Retryer.java:159-164,170-174`; `SimpleTimeLimiter.java:145-149,162-168,251-269`; `AttemptTimeLimiters.java:57-72,97-108`; `RetryerBuilder.java:208-213` (class predicates match `getExceptionCause().getClass()`).
- Probes: `timelimit/P4Executors`, `P5Duration`, `P6StackGrowth`, `P7Weird`, `P8Issue29`, `strategies/OutcomeProbe`.

**Affected code paths**: `Retryer.call` classification; `FixedAttemptTimeLimit`; `SimpleTimeLimiter.callWithTimeout` / `throwCause`; `ExceptionClassPredicate`.

**Suggested modeling approach**:
- Variables: per attempt `tag ∈ {Result, CallableExc, CallableError, Timeout, CallerInterrupted, Rejected, InvalidConfig}`, ghost `invoked[c][n]` (the body started); predicate configuration as the set of tags it matches (e.g. `retryIfException()` matches every non-`Error` tag; `retryIfRuntimeException()` matches Timeout, Rejected, InvalidConfig and runtime callable exceptions; `retryIfExceptionOfType(IOException)` matches only IOException callable failures).
- Actions: `Reject` (driven by Scenario 1's `shutdown` / full queue) and `Classify` produce the tag; no new actions otherwise.
- Granularity: classification is a single caller step after the limiter returns.
- D-10 is model-checkable through Scenario 1's executor model; D-11 … D-15 are configuration, unwrapping and policy details for code review and tests.

**Priority**: Medium
**Rationale**: Priority questions Q1/Q4; the attribution rule decides whether infrastructure failures are retried as if the callable ran (busy loops with 0 invocations) or end the call with a misleading `ExecutionException`; cheap to add as a tag on Scenario 1's attempts.

### Scenario 5: Post-attempt decision steps — undocumented exits and wait/stop arithmetic

**Mechanism**: listeners, predicate, stop check, wait computation and block run outside the attempt's try/catch, and nothing validates the computed sleep; built-in arithmetic (`join` sum, `exceptionWait` pass-through, the `int` attempt counter, incrementing and Fibonacci overflow, millisecond truncation) can produce values that end `call()` with an undocumented unchecked exception or a wrong count.

**Evidence**:
- Historical: #12 → PR #17 / `2b5bfec` (`join`, no overflow guard); #25 → PR #26 / `9c6bd63` (`exceptionWait`, no validation); PR #9 / `ce0bc7d` (Fibonacci guard `result < 0L`); the IncrementingWait clamp and the `int` counter come from `c531b61`; #93 (milliseconds). No fork fixed any of these.
- Code analysis: `WaitStrategies.java:225-230,365-371` (sum), `:386-394` (pass-through), `:273-284`, `:326-352`; `StopStrategies.java:85-88`; `Retryer.java:157,166-182`; `BlockStrategies.java:46`; `RetryException.java:34`.
- Probes: `strategies/EscapeProbe`, `IncProbe`, `FibScan`, `WrapProbe`, `RateProbe`, `StrategyMath`, `interrupt/IntProbe2` H2.6.
- Refuted in the same area: `RandomWaitStrategy`'s `Math.abs(nextLong())` can never be negative (exhaustive check of the 48-bit LCG: no state yields `Long.MIN_VALUE`); `ExponentialWaitStrategy` is monotone and capped (`Math.round` saturates); `stopAfterAttempt` stops exactly at N; `RetryException` count and cause are correct on both exits until the counter wraps.

**Affected code paths**: `CompositeWaitStrategy`, `ExceptionWaitStrategy`, `IncrementingWaitStrategy`, `FibonacciWaitStrategy`, `StopAfterDelayStrategy`, `ThreadSleepStrategy`, `Retryer.call` steps 4–9.

**Suggested modeling approach**:
- Variables: none beyond the decision-order `pc` and `outcome[c]`; the computed sleep can be abstracted to `{Zero, Positive}`. An optional third value `Invalid` (negative or null) may be offered as an environment choice only to check that the block step composes with interrupts (IAE preempts `RetryException` + flag); it does not by itself establish D-16 … D-18.
- Actions: `ComputeWait`, `Block` (as in Scenario 2).
- Granularity: single steps; do not model the arithmetic or a 2^31 counter.

**Priority**: Low (for TLA+)
**Rationale**: Priority questions Q4/Q5; deterministic arithmetic and validation defects, already probe-reproduced; code review and unit tests confirm them more directly than model checking. All rows stay in the ledger.

## 3. Modeling Recommendations

### 3.1 Model (with rationale)

| What | Why | How |
|------|-----|-----|
| `Retryer.call` decision loop with § 1.1 granularity, bounded attempts | Every Scenario attaches to these steps; C1, C3, C4 | Per-caller `pc`; `stopAfterAttempt(K)` as an attempt bound (K = 2–3), `neverStop` as a configuration; `stopAfterDelay` as an abstract elapsed-time flag checked only after an attempt (documented overshoot) |
| Time-limited attempt handoff (Submit / Wait / TimeoutDecide / Cancel / Classify) and the worker side of `FutureTask` | Scenario 1, D-1 … D-4 | FutureTask state machine per task; separate actions at the § 1.2 boundaries (i)–(iv) |
| Executors: cached (new worker per submit when none idle), bounded (N workers, queue Q, abort), shutdown flag; TPE clears a stale interrupt before the next task | D-3, D-4, D-10; regression check that cancellation interrupts stay contained | `workers`, `queue`, `capacity`, `shutdown`; `ClearInterrupt` step for TPE (a non-clearing executor variant is environment, see § 3.2) |
| Callable behaviors | Assumption: arbitrary user code | Nondeterministic per attempt: returns, throws (Exception / Error), honors interrupt, ignores interrupt, blocks forever |
| Caller and worker interrupt flags; environment `Interrupt` and `CancelOuter` | Scenario 2, D-5 … D-7 | Bounded budget; the flag is tested/cleared exactly where § 1.1/§ 1.2 say (`Future.get` when not done, `Thread.sleep` incl. 0, interruptible callable) and re-set only at `Retryer.java:180` |
| Shared listener list and builder thread | Scenario 3, D-8, D-9 | `blist`, `bmod`, `cfgAtBuild`, iterator steps; builder `AddListener` / `Build` |
| Attempt classification tags and `invoked` ghost | Scenario 4, D-10 (and the attribution parts of D-4/D-5) | Tag per attempt; predicate configuration as a tag set |
| Call outcome and exit-time interrupt flag | C3; invariants in § 5 | `outcome[c] ∈ {Returned, ExecExc, RetryExc, CME, OtherUnchecked}` plus `flagAtExit[c]` |
| Two callers sharing one Retryer and one limiter executor; one `wrap()` task on an outer executor | Must-cover sharing interaction; D-4, D-7, D-8 | `Callers = {c1, c2}`; an outer-executor worker that runs `call()` for the `wrap()` case |

**How the components interact** (including error, cancellation and cleanup paths): the caller submits the attempt and parks; the worker runs the body; exactly one of {body completes and `set` wins, deadline / caller interrupt makes the caller `cancel`} decides the task state, but the caller's classification depends only on which way `get` ended, not on whether `cancel` won (D-2). Cancellation interrupts the worker but nothing waits for it (D-1); a cancelled task left in a bounded queue still occupies capacity (D-4); a worker that ignores the interrupt keeps a thread until the body ends (D-3); TPE clears the interrupt before the next task (containment). The classified attempt then flows through the listener loop (which reads the builder's live list, D-8/D-9), the predicate (which decides on the tag, Scenario 4), the stop check and the sleep (the only interrupt restore point, Scenario 2). An outer `wrap()` executor's `cancel(true)` / `shutdownNow` arrives only as an interrupt on the thread running `call()` (D-7).

**Suggested configuration**: callers 1–2; attempts ≤ 3; executor ∈ {Cached with ≤ 3 threads, Bounded N=1 Q=1}; interrupt budget 1; one `AddListener` after `Build`; callable behaviors restricted per run to keep the state space small (e.g. {returns, ignores-interrupt} for D-1/D-2, {honors-interrupt} for D-5/D-7).

**Trace validation (Category B)**: record per-thread JVM-level events without modifying library source — via a JPF listener (`methodEntered`/`methodExited` and field reads of `FutureTask.state`) or wrapper instrumentation of user-side objects (callable, listener, executor, block strategy):
`call.enter(thread, flag)`, `attempt.submit(n) / reject`, `worker.start(n, thread)`, `body.enter / body.exit(n, outcome, interrupted?)`, `task.setCAS(n, won?)`, `get.exit(n, value | exception | timeout | interrupted)`, `cancel(n, returned)`, `thread.interrupt(target)`, `worker.clearInterrupt`, `listener.notify(id, cursor)`, `builder.add(id, size, modCount)`, `builder.build(retryer)`, `predicate(result)`, `stop(result)`, `computeSleep(value class)`, `block.enter(value) / block.exit(normal | interrupted | IAE)`, `outer.cancel`, `call.exit(kind, flag, attemptNumber)`.
JPF notes (from the guidance's environment): JDK 11 is required; jpf-core branch `local/reachability-fence` carries the `FutureTask` VarHandle fixes; JPF explores `parkNanos` timeouts nondeterministically (the smoke run reached all three timeout outcomes), and its spurious-wakeup policy covers only `Object.wait`, not `LockSupport.park` used by `FutureTask`/`ThreadPoolExecutor`.

### 3.2 Do Not Model (with rationale)

| What | Why |
|------|-----|
| Wait/stop arithmetic: `join` overflow, `exceptionWait` negative/null, incrementing and Fibonacci overflow, sub-ms truncation (D-16 … D-18, D-20 … D-22) | Deterministic value computations with no interleaving; probe-reproduced; code review and unit tests confirm them directly. Model only the abstract sleep class (§ Scenario 5). |
| The `int` attempt-counter wrap (D-19) | Needs 2^31 steps; a narrowed counter would only re-prove arithmetic. CR. |
| Stack-trace mutation (D-12), non-`Exception` Throwable wrapping (D-13), duration validation (D-11), `Error` handling policy (D-15, #67), `RetryException` serialization (D-23) | Library-level API/validation behavior with no concurrency; CR. (`Error` may appear as a callable behavior tag, but the wrapping policy is not a model property.) |
| `RandomWaitStrategy` `Math.abs(Long.MIN_VALUE)` | Refuted: `java.util.Random.nextLong()` never returns `Long.MIN_VALUE` sequentially (0 of 65,536 candidate states), and with interleaved draws the first qualifying gap is 201,243 calls. |
| Exponential wait arithmetic; `stopAfterAttempt` boundary; `RetryException` count/cause | Verified correct (monotone, capped; stops exactly at N; count/cause right until the counter wraps). Kept only as baseline properties where cheap (MC-9). |
| `stopAfterDelay` overshoot by one sleep plus one attempt | Documented mechanism ("If an unsuccessful attempt is made, … check if the amount of time …", `StopStrategies.java:59-63,75-79`). Model elapsed time only abstractly. |
| JMM reorderings of the unsynchronized `ArrayList` (NPE / stale slot) | TLA+ and JPF are sequentially consistent; mention only as a note on D-8. |
| ForkJoinPool (`cancel(true)` never interrupts; JDK 11 `commonPool` may run the task inside `get`), direct / same-thread executors and `CallerRunsPolicy` (no limit enforced), custom executors that never clear interrupts (stale cancellation interrupt reaches the next attempt) | JDK executor semantics chosen by the user; probe-confirmed but environment, not library code. Note in the brief; do not add ledger rows. |
| `ThreadLocal` / thread-affinity changes when a limiter moves the callable to a worker (#72) | API semantics, outside the requested defect classes. |
| Guava ≥ 23 incompatibility (#94, #96) | Dependency-resolution problem — excluded by the guidance. |
| `%d` message formatting (#97), Javadoc `IllegalStateException` vs `IllegalArgumentException`, implicit-ms multiplier (#93), first exponential wait = 2×multiplier (#86), `RetryListener` naming (#47), checked `RetryException` (#2) | Message formatting, naming, docs or API ergonomics — excluded by the guidance. |
| User listeners / predicates / strategies throwing, a `BlockStrategy` that swallows interrupts, a null callable | Outside the assumption that user code honors its interface; null callable is caller misuse. |
| Performance: O(n) `fib()`, two threads per timed attempt (#18) | No correctness impact in reachable ranges. |
| `RetryerBuilder` used concurrently by several threads | The builder makes no thread-safety claim; only "builder modified after `build()` while a built Retryer runs" is in scope (Scenario 3). |
